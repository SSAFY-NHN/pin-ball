# PC WebGL 전체화면 성능 안정화 설계

## 1. 목적

Chrome PC WebGL 빌드에서 2560×1440 전체화면 전환 후 발생하는 렉을 재현하고 원인을 측정해, 현재 게임의 전투 규모와 화면 품질을 가능한 한 유지하면서 안정적인 프레임을 확보한다.

이번 작업은 새 게임 기능을 추가하지 않는다. 측정 없이 품질을 낮추거나 광범위하게 코드를 고치지 않고, CPU·GPU·GC·메모리·UI·VFX 병목을 분리한 뒤 증명된 원인만 최소 범위로 최적화한다.

## 2. 목표 환경과 성능 기준

- 엔진: Unity 6.0.0.79f1
- 플랫폼: PC WebGL
- 브라우저: Chrome 최신 안정 버전
- 기준 해상도:
  - 1920×1080 창 모드
  - 1920×1080 전체화면
  - 2560×1440 전체화면
- 최대 부하 조건:
  - 핀볼 10개
  - 적 8명
  - 아군 5명
  - 2배속
  - 60초 강화 증원과 90초 최후 공세 포함

목표는 1920×1080에서 60 FPS 유지, 2560×1440 전체화면에서 목표 60 FPS와 반복적인 50 FPS 미만 하락 방지다. 90초 공세 동안 지속적인 메모리 증가, 반복 GC 스파이크, 브라우저 콘솔 오류와 전체화면 전환 후 입력·UI 오류가 없어야 한다.

## 3. 관찰된 증상과 초기 가설

사용자가 Chrome에서 2560×1440 전체화면으로 플레이했을 때 렉을 관찰했다. 창 모드와 전체화면의 구체적인 프레임 수치는 아직 측정되지 않았으므로 원인은 확정하지 않는다.

현재 구조에서 확인한 초기 가설은 다음과 같다.

1. URP Render Scale 1.0에서 1440p 네이티브 픽셀 렌더링 비용이 증가한다.
2. HDR, 2D Renderer, 투명 VFX와 Shader Graph의 오버드로우가 해상도 증가에 비례해 커진다.
3. 1920×1080 기준 Canvas가 전체화면 변경 때 재빌드되거나 매 프레임 UI 갱신 비용을 만든다.
4. 공·유닛·팝업·전투 피드백의 Update/LateUpdate/FixedUpdate 비용이 2배속 최대 부하에서 CPU 병목을 만든다.
5. 전체화면 전환 시 WebGL 렌더 타깃 또는 메모리 재할당이 스파이크를 만든다.
6. 런타임의 VSync 1과 목표 프레임 120 설정 조합이 WebGL 프레임 정책과 불필요하게 충돌한다.

각 가설은 측정으로 `확인`, `기각`, `추가 확인` 상태를 기록한다.

## 4. 측정 시나리오

같은 웨이브, 같은 유닛 조합과 같은 게임 배속으로 다음 조건을 반복한다.

1. 1920×1080 창 모드
2. 1920×1080 전체화면
3. 2560×1440 전체화면
4. 2560×1440 전체화면에서 Render Scale 0.85 진단 비교
5. 필요한 경우에만 Render Scale 0.75 진단 비교

각 실행에서 다음 값을 기록한다.

- 평균 FPS, 최저 구간과 긴 프레임 발생 시점
- CPU Main Thread와 Render Thread 프레임 시간
- GPU 또는 렌더링 프레임 시간의 사용 가능한 근사값
- Batches, SetPass, 삼각형 수
- 프레임당 GC Alloc과 GC 발생 시점
- WebGL 메모리 사용량과 시간별 증가
- Canvas rebuild와 UI 갱신 비용
- 2D Light, HDR, 투명 VFX와 Shader Graph 비용
- 전체화면 진입·해제 직후 스파이크
- Chrome 콘솔의 WebGL·메모리 오류

Unity Editor 수치만으로 WebGL 성능을 통과 처리하지 않는다. Editor/Development Build 측정은 원인 분리에 사용하고 실제 Chrome WebGL 실행을 최종 기준으로 삼는다.

## 5. 원인 분리 순서

### 5.1 픽셀·GPU 비용

Render Scale 1.0과 0.85를 같은 1440p 전체화면 조건에서 비교한다. 프레임 시간이 유의하게 개선되면 픽셀·GPU 비용을 우선 원인으로 판단한다. 0.85에서도 목표에 미달할 때만 0.75를 추가 측정한다.

### 5.2 VFX와 투명 오버드로우

전투 VFX를 진단용으로 비활성화한 비교 실행을 한다. 개선 폭이 확인될 때만 개별 풀, 비활성 효과 갱신, 파티클 수명, 투명 레이어와 Shader Graph 비용을 세분화한다. 진단용 비활성 상태를 제품 동작으로 남기지 않는다.

### 5.3 UI와 Canvas

HUD, 콤보 표시, 구매 카드, 상태 표시, 팝업의 갱신 빈도와 Canvas rebuild를 확인한다. 매 프레임 문자열·레이아웃 변경이 실제 병목일 때만 상태 이벤트 또는 정수 초 변화 기준 갱신으로 좁힌다.

### 5.4 오브젝트 수와 CPU

핀볼, 적과 아군 수를 단계적으로 바꿔 프레임 시간 변화가 오브젝트 수에 비례하는지 확인한다. 비례 관계가 증명될 때만 타겟 탐색, Unit Update, 물리와 피드백 갱신을 조사한다. 최대 공 10·적 8·아군 5 규칙은 변경하지 않는다.

### 5.5 메모리와 전체화면 전환

전체화면 전환 전후와 90초 공세 동안 메모리를 비교한다. 지속 증가 또는 큰 재할당이 확인될 때만 풀 크기, 렌더 타깃과 WebGL 메모리 성장 설정을 조정한다.

## 6. 화면 조건 기반 품질 단계

GPU 픽셀 비용이 원인으로 확인된 경우, 매 프레임 FPS에 반응하는 동적 해상도 대신 화면 조건 기반의 안정적인 품질 단계를 적용한다.

- 1920×1080 이하: Render Scale 1.0
- 2560×1440 전체화면: Render Scale 0.85
- 0.85에서 목표 미달이 측정된 경우에만 0.75 검토
- 전체화면 해제 또는 해상도 감소: 1.0 복구
- 화면 전환 직후 한 번만 재평가
- 런타임 세션에만 적용하고 URP 원본 애셋 값을 영구 덮어쓰지 않음
- 새 런과 씬 전환 후 현재 화면 조건에 맞는 값 보장

잦은 렌더 타깃 재생성과 화질 출렁임을 막기 위해 프레임마다 품질 단계를 변경하지 않는다. HUD 글자, 버튼, 입력 좌표와 화면 비율은 별도로 검증하고 가능한 한 네이티브 해상도 가독성을 유지한다.

## 7. 최적화 적용 원칙

- 측정 결과가 증명한 병목만 수정한다.
- 한 번에 한 범주를 변경하고 같은 시나리오로 재측정한다.
- 기존 전투 규칙, 최대 오브젝트 수와 사용자 연출을 보존한다.
- 기존 풀링과 SetActive 수명 관리를 유지한다.
- 신규 외부 패키지를 추가하지 않는다.
- 사용자가 수정한 ProjectSettings와 애셋을 임의로 원복하거나 포함하지 않는다.
- 품질 저하는 전후 프레임과 가독성 비교 결과를 기록한다.
- 런타임 UI 자동 생성과 요청 없는 리팩터링을 하지 않는다.

## 8. 검증

정적·EditMode 검증은 다음을 다룬다.

- 화면 크기와 전체화면 조건에 따른 품질 단계 선택
- 1080p 이하 1.0 유지
- 1440p 전체화면에서 승인된 단계 적용
- 창 모드 복귀 시 1.0 복구
- 중복 적용과 매 프레임 애셋 변경 방지
- 씬 전환과 새 런 이후 현재 화면 조건 재적용
- 기존 UI 참조와 화면 비율 유지
- 최적화한 UI·VFX·전투 경로의 회귀 테스트

Unity와 Chrome 직접 검증은 다음을 다룬다.

- 세 기준 해상도의 같은 최대 부하 시나리오
- 2배속 90초 공세
- 전체화면 진입·해제 반복
- FPS, 프레임 시간, GC와 메모리
- UI 선명도, HUD 가독성, 버튼 입력 좌표
- VFX 누락, 풀링 오작동과 Missing Script/Reference
- Chrome 콘솔 오류

관련 EditMode, 전체 EditMode와 C# 컴파일을 실행한다. 기존 전체 EditMode 실패는 기준선과 비교해 새 회귀와 구분한다.

- 확인·기각된 가설 목록
- 실제 병목과 증거
- 적용한 최소 변경과 전후 차이

- `docs/ai-usage/YYYY-MM-DD/`의 실제 작업·검증 기록

## 10. 비범위

- 새 게임 기능과 콘텐츠
- 최대 핀볼·적·아군 수 감소
- 모든 PC에서 무조건 60 FPS 보장
- 측정 없는 전역 품질 하향
- 매 프레임 FPS 기반 동적 해상도
- 모바일 WebGL 최적화
- 외부 분석·최적화 패키지
- 광범위한 렌더 파이프라인 교체
- 요청 없는 UI 재설계

## 11. 사용자·병행 작업 변경 보존

현재 작업 트리의 사용자 및 병행 기지 스킬 구현 변경을 임의로 수정·원복·스테이징·커밋하지 않는다. 최적화 작업 시작과 종료 시 Git 상태를 비교하고, 계획에 명시된 파일만 다룬다.
